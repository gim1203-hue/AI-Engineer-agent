Prompt & Context Engineering: Getting Reliable Answers

A model can only work with what you give it. Prompt engineering is writing clear instructions; context engineering is choosing exactly what information goes into the model's context window.

What a prompt really is

A prompt is everything the model reads before it answers: the system prompt (standing instructions set by the developer), the conversation history, any documents or tool results you include, and the user's latest message. The model has no memory beyond this. If it isn't in the context, the model doesn't know it.

Treat the model like a very smart new colleague on their first day: talented, but with zero background on your project. Spell out what you want.

Anatomy of a good prompt

  • Role and goal: who the model is acting as and what success looks like.
  • Context: the facts, documents or data it needs.
  • Instructions: clear steps or rules, positive ("do X") rather than only negative.
  • Format: length, structure, tone. For example "3 bullet points, under 50 words".
  • Edge cases: what to do when information is missing ("say you don't know").

Examples (few-shot prompting)

Showing 2–5 examples of input → ideal output is often more effective than describing the format in words. The model copies the pattern: tone, length and structure. Use varied examples so it doesn't over-copy one detail.

Context engineering

Context windows are large but not free: more tokens means more cost, more latency, and sometimes worse focus. Context engineering is deciding what goes in:

  • Retrieve only the relevant documents (that's RAG, the next lesson).
  • Summarise long conversation history instead of resending everything.
  • Put the most important instructions at the start and repeat key constraints at the end of long prompts.
  • Separate data from instructions with clear tags like <document>, and tell the model the data is untrusted. This defends against prompt injection.

Getting structured output

Apps often need JSON, not prose. Ask for an exact schema, give an example, and use the API's structured-output or tool-calling features where available. Always validate the result in code; never assume it's perfect.

Common mistakes

  • Vague goals ("make it better") with no success criteria.
  • Testing a prompt on one example and calling it done. Build a small eval set of 20+ cases.
  • Stuffing the whole database into the prompt instead of retrieving what's relevant.
  • Mixing untrusted user or web content with instructions.
